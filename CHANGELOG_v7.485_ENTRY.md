## v7.485 — 2026-09-04

### Password recovery: a one-time reset link, and an eye on every password field

- **Wayne asked whether user passwords are saved, and whether an eye icon could show the existing one.** They are not saved: since v7.373 a password is stored as a one-way scrypt hash (`scrypt$<salt>$<key>`), so **there is nothing to reveal** — not to an admin, not to the app, not to anyone with the database. An eye that showed a stored password would require storing it recoverably, which is the wrong trade. So recovery here **issues a new secret** instead of reading an old one.
- **Every password field is now masked with a reveal toggle.** Both admin fields were `type="text"` — a temporary password sat in plain sight of anyone near the screen. They are masked now, and the eye reveals **what the operator is typing**, so it can still be checked before saving. The sign-in field gets the same toggle. One shared `PasswordField` component, so the two admin call sites cannot drift apart.
- **"Create reset link" on any user's Manage drawer.** It mints a single-use link the admin copies and hands over. OrbitIQ has no mail sender — no SMTP, Resend or SES dependency, and no env var for one — so the link is delivered by the operator, and the panel **says so on its face** rather than implying an email went out.
- **What the token actually is.** 32 bytes of `crypto.randomBytes` (256 bits), base64url. **Only its SHA-256 reaches the database** — the same one-way property the password column has, so a leak of `password_resets` yields no working link. Lookup is by hash, the compare is `timingSafeEqual`, and the plaintext exists only in the response that hands the link over.
- **Single-use, 30 minutes, and replaceable.** Spending a token is an `UPDATE … WHERE used_at IS NULL … RETURNING`, so two simultaneous submissions race on one row and exactly one wins — a double-click cannot set a password twice. The token is **spent before** the password is written, never after. Issuing a new link invalidates any prior unused one, so a mis-sent link stops working the moment it is replaced.
- **A successful reset revokes every existing session** for that account. Resetting a password that must not leave an older session alive is the entire point.
- **Invalid, expired and already-used all return the same message**, so the endpoint cannot be used to probe which tokens ever existed.
- **`/reset-password` is public by design** — the person using it cannot sign in, which is why they are there. The one-time token in the URL is the only credential, and every guard on it lives server-side in `/api/auth/reset`.
- **The single-owner lockout warning.** With exactly one active owner, the Users tab now says so: that account can issue a reset link for anyone, but nobody can issue one for it. Counted from the real user rows (Const I.1) and it disappears the moment a second owner exists — a real condition, not decoration.
- **Sign-in stops being silent about it.** It now states that passwords cannot be looked up and that an admin issues reset links, instead of leaving a locked-out person with no next step.

**Downstream parity (II.6a/II.6b)** — this release adds no client-facing metric and no left-nav panel; it changes the operator-only auth surfaces (`/admin`, `/sign-in`, `/reset-password`), exactly as v7.373 (login) and v7.418 (user groups) did, neither of which has an Assessment PDF section. No PDF, delivery package, PPT prompt or client export reads anything added here, and none was changed. Not a II.6b deferral — there is no client-facing metric to defer.

**Verification** — real project `tsc` clean and the real `next build` compiles all 16 routes including the two new ones (Const V.1a); 68 new retained-suite checks (42 logic + 26 jsdom driven with real clicks), **all of which fail on the pristine v7.484 base** — proven by an A/B run with the change stashed; retained suite **zero regression delta** (34 pre-existing failures, identical names on both sides). Rendered in Chromium in both themes and contrast-measured against v7.484's own markup as the control: every new element matches its incumbent equivalent (`text-orbit-tertiary` 2.61:1 dark on both), and the one element with no incumbent — the "Create reset link" ghost button — was moved from `text-orbit-accent` to `text-orbit-accent-light`, which raises contrast in **both** themes (5.9:1 dark, 9.68:1 light) because that token is lighter in dark and darker in light.

**Known gap, stated rather than hidden (Const I.5):** there is still no self-serve "Forgot password?" flow, because there is still no mail sender. Wayne chose the admin-issued link for this release; adding email later changes only *who* calls `mintResetToken()` — the token contract, the page and every guard are unchanged.
